# ADR-0008: Build-time generation (the `ferrobridge-build` `generate` feature) and the GPL demo

**Date**: 2026-11-27
**Status**: accepted
**Deciders**: Alper (project owner)

## Context

Per ADR-0004, generated bridges are committed; this keeps FFI code visible and reviewable. M5's real-world demo binds ArduPilot's `AP_Math` library. ArduPilot is licensed under GPL-3.0. Per ADR-0003, GPL code is not copied into this repository. The `bridge.rs` and `shim.*` generated from ArduPilot headers, however, derive from ArduPilot's declarations, names and documentation. Committing them would bring GPL-derived text into the repository. The demo's own Rust code also links against a GPL library.

## Decision

1. **`ferrobridge-build` offers two modes.**
   - The default mode compiles committed files. This is ADR-0004's path; no libclang needed.
   - The mode enabled by the `generate` feature reads the header with libclang inside `build.rs`. It generates the bridge under `$OUT_DIR/ferrobridge/<name>/` and compiles it. The Rust side uses it with `ferrobridge::include_bridge!("<name>")`.
2. **The demo lives under `demo/ap_math/` as a separate Cargo workspace.**
   - Its license is `GPL-3.0-or-later`, with its own `LICENSE` file; `publish = false`.
   - It points to ArduPilot from outside with `ARDUPILOT_DIR`.
   - It uses the `generate` mode. No generated file is committed.
3. **ferrobridge's own crates stay `MIT OR Apache-2.0`.** The root workspace does not include the demo; `cargo test --workspace` does not need ArduPilot.

## Alternatives considered

### Alternative 1: setting up the demo with committed files per ADR-0004 as well
- **Pros**: One path; the demo's bridge is reviewable too.
- **Cons**: GPL-derived generated text enters the repository; files must be regenerated by hand when ArduPilot is updated.
- **Why not chosen**: The license separation (ADR-0003) matters more.

### Alternative 2: putting the demo in a separate repository
- **Pros**: Complete license separation; no GPL file at all in the main repository.
- **Cons**: The demo and the generator cannot change in the same commit; a broken demo is noticed late.
- **Why not chosen**: Throughout M5–M6 the demo is the generator's main real-world test. A separate workspace and a separate license file give enough separation. Can be reconsidered before the release (M7).

### Alternative 3: not offering build-time generation at all
- **Pros**: ADR-0004 stays the only rule.
- **Cons**: No path for users who cannot commit generated files because of their license or size.
- **Why not chosen**: A real need; offering it as an explicit feature (`generate`) does not change the default.

## Consequences

### Positive
- No GPL-derived generated file in the repository. `demo/ap_math/.gitignore` excludes `target/`.
- `ferrobridge-build` supports both the committed path and build-time generation. `ferrobridge-e2e` tests the committed path, and an integration test (`crates/ferrobridge-build/tests/generate_mode.rs`) tests the generation path.

### Negative
- Code generated in `generate` mode is not visible in the repository. The files sit in `OUT_DIR`; unbound items and assumptions are listed at the top of the file. `build.rs` prints the file's path in a summary warning per bridge.
- `generate` mode needs libclang on every build. The bridge can change when the libclang version changes; this is the situation ADR-0004 avoids, and it is accepted deliberately for this mode.

### Risks
- **A generated file committed by accident.** Mitigation: the demo generates only into `OUT_DIR`, and `target/` is ignored.
- **The demo's own code is GPL.** Demo code must not be moved into the main crates.
- **The generating machine differing from the building machine (in committed mode).** This was handled separately in M5:
  - Constants involving `sizeof`/`alignof`/`offsetof` are rejected.
  - Integer constants are re-checked at compile time with `static_assert` in `shim.cc`.
