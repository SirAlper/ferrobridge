# ADR-0012: Release and versioning policy

**Date**: 2026-11-27
**Status**: accepted
**Deciders**: Alper (project owner)

## Context

v0.1 is the first release on crates.io. ferrobridge is a workspace of seven crates: the `ferrobridge` runtime, `ferrobridge-build`, the `ferrobridge` command (`ferrobridge-cli`) and four internal crates (`-ir`, `-parser`, `-analysis`, `-codegen`). `ferrobridge-cli` and `ferrobridge-build` depend on the internal crates, so those must be published too. Generated code (`bridge.rs`) is committed in users' repositories (ADR-0004) and calls helpers in the `ferrobridge` runtime crate; a user can upgrade the runtime without regenerating, and the two can drift apart silently. Publishing to crates.io cannot be undone (a version can only be yanked).

## Decision

1. **One version for all crates (lockstep).** Every release publishes all seven crates with the same version; internal dependencies are pinned exactly (`version = "=0.1.0"` in `[workspace.dependencies]`).
2. **Public API:** `ferrobridge`, `ferrobridge-build` and the `ferrobridge` command. The internal crates are published as implementation details; their READMEs and crate docs say there is no stability guarantee.
3. **Compatibility rule:** code generated by ferrobridge `0.x.y` needs the `ferrobridge` runtime at `0.x` (the same minor version). While on `0.x`, a minor release may change the generated code and the runtime; a patch release does not. The first line of every generated file names the generator version (`// @generated by ferrobridge 0.1.0 — …`), so the generator that produced a file is visible.
4. **Publishing is manual** for now: the project owner runs `cargo publish --workspace` after the checklist in `docs/releasing.md` (dry run, a quickstart crate outside the repository). No crates.io token is stored in CI.
5. **Minimum versions are tested, not only stated:** Rust 1.85 (`rust-version`) and libclang 16 each have a CI job.

## Alternatives considered

### Alternative 1: merge the internal crates into one published crate
- **Pros**: fewer crates on crates.io; a smaller public surface.
- **Cons**: breaks the rule that `ferrobridge-ir` depends on no other ferrobridge crate; a large refactor right before the release.
- **Why not chosen**: The same effect (no stability promise) comes from documentation and exact pins.

### Alternative 2: independent versions per crate
- **Pros**: a crate that did not change does not get a new version.
- **Cons**: users and maintainers must track which versions work together; the compatibility rule becomes a table.
- **Why not chosen**: The crates change together in practice; one number is simpler for v0.x.

### Alternative 3: a runtime version check in the generated code (e.g. a `const` assertion against the runtime's version)
- **Pros**: a mismatch becomes a compile error instead of a possible confusing type error.
- **Cons**: needs a versioned item in the runtime API and changes every generated file's code, not only its comment.
- **Why not chosen**: Not needed for the first release; can be added when the first incompatible change happens.

### Alternative 4: publishing from CI on a tag
- **Pros**: repeatable, no local state.
- **Cons**: a long-lived token in CI for a project with one maintainer; the first publish of new crate names is easier to watch by hand.
- **Why not chosen**: Can be revisited after a few releases.

## Consequences

### Positive
- A user needs to know one version number.
- The generator version is visible in every committed generated file.
- The documented minimum Rust and libclang versions are checked on every push.

### Negative
- Every release changes the first line of every generated file, including the committed e2e files and snapshots.
- A release publishes seven crates even if only one changed.

### Risks
- A user upgrades the runtime to a new minor version without regenerating → type or link errors in generated code. Mitigation: the version rule in the README and the crate docs; the version in the generated header; Alternative 3 if this happens in practice.
- A broken crate is published. Mitigation: `cargo package` builds every crate from its archive in CI; the release checklist runs a quickstart crate outside the repository against the packaged crates before publishing.
