# ADR-0004: Generated code is written to files and committed

**Date**: 2026-11-27
**Status**: accepted
**Deciders**: Alper (project owner)

## Context

From a C++ header ferrobridge generates `bridge.rs` (the cxx bridge), `shim.h` and `shim.cc`. These files can come into being in two ways: the user's `build.rs` regenerates them on every build (the bindgen/autocxx approach), or the user generates them once with a command and puts them under version control. The generated code sits on the FFI boundary; which function is bound with which type and under which safety assumption is information the user needs to see and review.

## Decision

Code is generated with `ferrobridge generate <header> --out-dir <dir>`; the files are written to disk and committed to the user's repository. Every file starts with `// @generated by ferrobridge` and lists the items that were not bound, with reasons. `generate` does not overwrite a file without this marker unless `--force` is given.

## Alternatives considered

### Alternative 1: generating in `build.rs` on every build
- **Pros**: The code updates itself when the header changes; no generated files in the repository.
- **Cons**: Every build needs libclang (CI and end-user machines included); the generated code is invisible and cannot be reviewed; the bridge can change silently when the libclang version changes.
- **Why not chosen**: FFI code is safety-critical, so it being visible and reviewable comes first.

### Alternative 2: offering both
- **Pros**: Flexibility.
- **Cons**: Both paths need testing and documentation; unnecessary load for the MVP.
- **Why not chosen**: The `build.rs` helper (`ferrobridge-build`) arrived in M5 in line with this ADR, compiling only committed files by default. Generating on every build was added by ADR-0008 as an explicit feature (`generate`) for code that cannot be committed because of its license; the default path is this ADR.

## Consequences

### Positive
- The user sees and reviews the bridge in a PR; changes show up in the diff.
- Building needs no libclang; only the developer who runs `generate` needs it.
- The repository's `ferrobridge-e2e` crate uses the same model, and a test checks that the committed files match the generator's current output.

### Negative
- The user may forget to rerun `generate` when the header changes.
- Generated files take up space in the repository.

### Risks
- **Drift between the header and the generated code.** Mitigation: users will be advised to compare `generate`'s output with the committed files in their own CI (the test doing this in ferrobridge's own repository serves as an example); a `ferrobridge check` command may be considered later.
