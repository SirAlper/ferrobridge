## Summary
The tool works (M1–M6) and the repo is public with green CI, but nothing can be installed from crates.io yet:
every crate has `publish = false`, version `0.0.0`, and most have no description, repository link or README.
The README tells users to run `cargo run -p ferrobridge-cli` from a clone.

M7 turns this into a release a stranger can use:
- `cargo install ferrobridge-cli` gives the `ferrobridge` command.
- `ferrobridge = "0.1"` and `ferrobridge-build = "0.1"` work in a new crate, following only the README.
- The claims in the README are checked by CI: minimum libclang **16** and minimum Rust **1.85** are tested, not only stated.
- A `CHANGELOG.md`, a `v0.1.0` tag and a GitHub release exist.

**Measurable goal (PRD):** "The tool is on crates.io; README, examples and demo are public."
Checked by: the 7 crates are on crates.io, docs.rs builds the public crates, and a crate created outside
the repo builds and runs by following the README with the published versions.

## Findings while grounding the plan
- **Names:** all 7 names are free on crates.io (checked 2026-11-27: `ferrobridge`, `ferrobridge-ir`,
  `-parser`, `-analysis`, `-codegen`, `-build`, `-cli` return 404). This answers the PRD's open question
  "will the project name be finalized?" if we keep `ferrobridge`.
- **Packaging blockers:** no `include_str!`/`../` paths in the published crates (only `ferrobridge-e2e`,
  which stays unpublished). The workspace path dependencies have no `version`, which `cargo publish` requires.
- **Generated files carry no ferrobridge version.** A version bump does not change
  `crates/ferrobridge-e2e/src/generated/`. Compatibility between generated code and the `ferrobridge`
  runtime crate is therefore implicit today (see decision 3).
- **Unverified claims:** CI uses libclang 18 (Ubuntu) and 23 (Homebrew); the minimum 16 has never run.
  `rust-version = "1.85"` has never been checked (local toolchain is 1.100, `syn` is 3.x).
- `cargo-deny` / `cargo-audit` are not installed; no dependency or license scan has ever been run.

## Decisions (need your approval)
1. **Keep the name `ferrobridge`.** All names are free; the open PRD question is closed.
2. **Publish all 7 crates, one shared version (lockstep), `0.1.0`.**
   - `ferrobridge-cli` and `ferrobridge-build` depend on the internal crates, so those must be on crates.io too.
   - Public, documented API: `ferrobridge` (runtime), `ferrobridge-build`, the `ferrobridge` command.
   - `ferrobridge-ir`, `-parser`, `-analysis`, `-codegen` are published as implementation details:
     their READMEs and crate docs say "no stability guarantee; use `ferrobridge-build` or the CLI".
   - Alternative considered: merging the internal crates into one. More work, breaks the `ir` isolation
     rule, gains nothing for v0.1; not chosen.
3. **Generated code ↔ runtime compatibility rule (ADR-0012).** Code generated by ferrobridge `0.x.y`
   needs the `ferrobridge` runtime `0.x` (same minor). The generated file header gets the generator version
   (`// @generated by ferrobridge 0.1.0`) so a mismatch is visible. This changes every committed generated
   file once (regenerate e2e).
4. **Publishing is manual, done by you.** `cargo publish` needs your crates.io token and cannot be undone
   (only yanked), so I prepare everything and run `cargo publish --dry-run`; you run `cargo login` and
   the real `cargo publish --workspace` (or give me an explicit go-ahead after logging in).
   No publish token in CI for v0.1; the steps go into `docs/releasing.md`.
5. **Announcement is drafted, not posted.** I draft short texts (users.rust-lang.org, r/rust,
   ArduPilot Discourse); you post them.

## Patterns to Mirror
| Category | Source | Pattern |
|---|---|---|
| Manifest | `Cargo.toml:5` (`[workspace.package]`) | Shared fields live in the workspace and are inherited with `.workspace = true` |
| Manifest | `crates/ferrobridge-build/Cargo.toml:3` | A one-sentence `description` that says what the crate is for |
| Internal deps | `Cargo.toml:21` (`[workspace.dependencies]`) | Internal crates declared once in the workspace; the graph comment stays current |
| Docs | `README.md` "Usage" | Command block, then a table of what was written, then the rule behind it with an ADR reference |
| ADR | `docs/adr/template.md`, `docs/adr/0011-libraries-without-exceptions.md` | Context → decision → alternatives → consequences; index row in `docs/adr/README.md` |
| Generated header | `crates/ferrobridge-e2e/src/generated/classes/bridge.rs:1` | `// @generated by ferrobridge — do not edit by hand…` first line |
| Tests | `crates/ferrobridge-cli/tests/generate.rs` | CLI integration tests; the e2e sync test catches stale generated files |
| CI | `.github/workflows/ci.yml` (`test` job) | One job per concern, Linux + macOS matrix, `LIBCLANG_PATH` set per OS |
| Errors | n/a | No new error paths expected; if one appears, mirror `thiserror` enums in `ferrobridge-build` |

### CI fix (2026-11-28): libclang 16
- The new `libclang-min` job found a real difference: libclang before 17 reports `extern "C" { ... }` as `UnexposedDecl`, not `LinkageSpec`, so `c_api_version` in the `namespaces` fixture was reported as unsupported (not silently skipped, but not bound either).
- Fix: `is_linkage_spec` in `lower.rs` also accepts an `UnexposedDecl` whose first two tokens are `extern` and a string literal (so `extern template ...` is not mistaken for it); used both when visiting declarations and when walking a declaration's scope. New `Cursor::leading_tokens` in `clang.rs` (`clang_tokenize`, tokens released once).
- Verified locally with Homebrew `llvm@16`: the `namespaces` snapshot matches. **Finding:** on macOS, libclang 16 cannot read the libc++ headers of the current Xcode SDK (`__builtin_clzg` and similar are missing), so every fixture using `<string>`/`<vector>` fails to parse there, with a clear diagnostic. Not a ferrobridge bug; documented in the README and CHANGELOG (the minimum of 16 holds with libstdc++ on Linux, which CI checks).
